[Node 24.22.3](https://nodejs.org/en/blog/release/v24.22.3) · [Next.js 16.4](https://nextjs.org/blog/next-16-4) · [ESLint version support](https://eslint.org/version-support/)

The gateway's three tests passed under `npm test -w @quotacarry/gateway`, covering config validation, readiness, request correlation, log redaction by field allowlist, and the draining response. ESLint supplies the globs in this repository's fixed local/CI commands. Keep the supported ESLint version and update when its dependency range picks up the fix. - Gitleaks 8.30.0 `dir --redact --no-banner` found no leaks in a snapshot of Git-visible files. `git check-ignore` verified local environment files, key files and NEAR credentials are excluded. `git rev-list --all --count` reported zero commits. CI will scan tracked files and history on GitHub.
- Rust/Cargo 1.99.1, NEAR SDK and contract standards 5.30.1, Cargo NEAR 0.23.0. `cargo generate-lockfile` and `cargo fmt --check` passed. Early host and WASM builds failed because Windows lacked `link.exe`. WSL was unavailable. The minimal build uses `--no-abi` to keep Phase 0 focused on the WASM artifact. ## NEAR and deployment feasibility

**Rust verification blocker.** Visual Studio Build Tools 17.14.45 and the Windows SDK supplied the missing native linker and libraries. Intermediate retries during installation failed on `kernel32.lib` and `dbghelp.lib`. After those were available, Cargo NEAR successfully invoked the compiler and linker, but Windows Application Control blocked execution of Cargo-generated dependency build scripts (OS error 4551). The WASM artifact, Rust unit tests and Clippy remain unverified. Rerun the documented Rust commands on a policy-approved Linux runner or a Windows environment authorized to execute Cargo build scripts. GitHub Actions is configured for Linux but has not run.

- Read-only JSON-RPC `block` with `finality: final` succeeded on `https://rpc.testnet.near.org` at height 277485945 (hash `83nXqBGgdc29cdWuQVURRfNM39Ee2tnJXSN4SZPQ18jo`) and `https://test.rpc.fastnear.com` at 277485947 (hash `DueMz3saYNeygmcSbvb5CXAZEVFLBAmqV7tP5nB8QkeL`). FastNEAR also returned the same hash as the first RPC for the exact height 277485945. Neardata `GET https://testnet.neardata.xyz/v0/block/277485945` returned that hash and 10 shard payloads. This verifies recent history feasibility. Archive retention, continuity and third-party QuotaCarry event coverage remain deployment checks. [RPC providers](https://docs.near.org/api/rpc/providers) · [Neardata](https://docs.fastnear.com/neardata)
- Transaction consumers must query `FINAL` and validate successful relevant receipt outcomes, contract, inputs or events and resulting state. Inclusion alone does not establish execution. Use indexer projections for history only. [Transaction RPC](https://docs.near.org/api/rpc/transactions)
- NEAR Connect (registry candidate `@hot-labs/near-connect@0.12.0`) exposes separate `signMessage` and testnet capability flags. Wallet Selector is a fallback. Before freezing either connector, test two wallet accounts with the exact NEP-413 bytes, recipient, nonce, optional callback, signature encoding, full-access key lookup and wrong-network rejection. Wallet manifest flags alone do not establish that a wallet works end to end. [NEAR Connect](https://github.com/azbang/near-connect) · [NEP-413](https://github.com/near/NEPs/blob/master/neps/nep-0413.md)
- Testnet deployment requires the verified WASM artifact, separately controlled deployer and issuer accounts with enough testnet NEAR for gas and storage, an approved signer, initialization/upgrade plan, registered authorizer/settler and two wallet accounts for handoff tests. Record compiler, artifact hash and successful finalized receipts. Hosted deployment additionally needs a persistent worker, PostgreSQL, managed secrets, TLS and protected environment configuration. Phase 0 makes only public reads. [Deployment guide](https://docs.near.org/web3-apps/tutorials/mastering-near/1.3-deploy)
- Reviewed the official NEAR smart-contract skill source without installing a new agent plugin. QuotaCarry contract semantics and Workspaces receiver integration tests are Phase 1 deliverables. The [risk ADR](ADR-0001-FOUNDATION.md) defines the gate. [NEAR skill source](https://github.com/near/agent-skills/tree/main/skills/near-smart-contracts)

## Provider feasibility

| Provider | Documented request shape and candidate | Account-specific validation required |
|---|---|---|
| Groq | Bearer token, `POST https://api.groq.com/openai/v1/chat/completions`, candidate `openai/gpt-oss-20b`. Use `max_completion_tokens`, chat usage counts and response rate-limit headers. The model catalog lists developer limits of 1,000 RPM and 250,000 TPM. [API](https://console.groq.com/docs/api-reference) · [Models](https://console.groq.com/docs/models) · [Rate limits](https://console.groq.com/docs/rate-limits) | Check project access, real bounded completion including reasoning, effective quotas and usage, 429 and billing behavior, provider spend controls and sponsored-use terms. |
| Gemini | `x-goog-api-key`, `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`, candidate `gemini-3.5-flash-lite`. Inspect `usageMetadata`, including prompt, candidate and thinking counts. `maxOutputTokens` and supported thinking controls need a joint cap check. RPM, TPM and RPD depend on the project and tier. [API](https://ai.google.dev/api/generate-content) · [Model](https://aistudio.google.com/docs/models/gemini-3.5-flash-lite) · [Limits](https://ai.google.dev/gemini-api/docs/rate-limits) | Confirm model access, thinking/output ceiling, region, paid-project eligibility, retention and effective quotas. |
| NEAR AI Cloud | Bearer token, `POST https://cloud-api.near.ai/v1/chat/completions`, documented example `zai-org/GLM-5.1-FP8`. Chat usage includes prompt and completion fields plus reasoning when returned. The provider documents distinct gateway and model signature evidence. [Quickstart](https://docs.near.ai/cloud/quickstart) · [Response signatures](https://docs.near.ai/cloud/verification/cloud-api/response-signatures) | Confirm canonical model visibility, generated-token cap, effective rate limits and organization budget. Verify a live signature before claiming attestation for the configured route. |

All three providers remain documentation-verified candidates. There were no credentialed calls. For later smoke tests, create a scoped key in the provider's dedicated project, apply budget and model controls, and store it directly in the approved secret manager. Grant only the worker service identity read access. Never paste credentials into chat or commit a local secret file. The architecture plan records required privacy and provider terms review. Model IDs, wallet versions, measured latency, token limits and production readiness remain provisional until their corresponding checks pass.
