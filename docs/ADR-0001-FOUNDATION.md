# ADR 0001 — Reservation authorization and launch gates

## Restricted relayer

The contract will enforce the issuer authorizer identity, current holder, epoch, sequence, deadline, lock and balance in one receipt. The relayer is trusted to assert that the named holder actually requested each new reservation. A compromised relayer can impersonate a current holder using fresh sequence/epoch values and consume or lock available credits via permitted calls. It cannot use a stale owner/epoch to pass the same check, transfer an NFT, or settle using the authorizer key alone. The gateway and settlement role remain trusted for upstream dispatch and disposition. Use isolated limited keys, bounded gas and liabilities, rotation, pause and auditing. The initial design is permissioned.

A wallet-signed permit would bind a versioned domain, network, contract, issuer/policy, holder, token, epoch, sequence or unique nonce, maximum amount, request commitment and expiry. Verify canonical signed bytes, current owner/epoch, approved signing key and monotone sequence in the reservation receipt. Use a holder-controlled on-chain permit key registration, epoch-bound authorization and explicit revocation. NEP-413 login proves identity to the gateway using RPC key membership. Contract verification of an arbitrary signature alone cannot prove live NEAR access-key membership. A registered permit key needs its own rotation and removal semantics. Permit signing reduces relayer impersonation, adds wallet compatibility and approval latency, and leaves dispatch/settlement trust in place. Evaluate against direct holder-signed calls and the restricted relayer with real wallets. Require replay, wrong scope, wrong key, revoked key, expired, transfer-away-and-back and payload substitution tests before enabling permits. Keep the initial relayer pending that evaluation.

## NEP-171 compatibility gate

**Decision.** Preserve the pinned NEP-171 ownership behavior and gate compute separately. `nft_transfer_call` changes the NFT owner immediately, updates enumeration, increments the ownership epoch and creates a unique pending resolver entry before scheduling the receiver. While any entry remains, the reported NFT owner can perform standard NFT transfers, including onward transfer-call. A subsequent plain or callback transfer increments the epoch and carries the pending entries forward. The hold applies to reserve, split and merge, independent of current owner.

Each private resolver is bound to its own entry and processes it once. Receiver false accepts. Receiver true, failure or malformed return requests rollback. Follow the pinned resolver's current-owner rule: restore the previous owner only if the receiver still owns the token at resolution, even after an away-and-back path. If another account owns it, preserve that owner. Increment the epoch on actual restoration and emit the reverse transfer. Resolution removes only its entry. Compute resumes for the actual current owner once all entries clear. Existing reservations remain keyed to the token and sequence. Settlement and eligible refunds continue during the hold and apply to the same token. If a resolver itself fails, keep the compute hold, expose quarantine, and require reviewed reconciliation against finalized evidence. Standard onward transfers remain available. [NEP-171](https://github.com/near/NEPs/blob/master/neps/nep-0171.md) · [Pinned reference resolver](https://raw.githubusercontent.com/near/near-sdk-rs/near-sdk-v5.30.1/near-contract-standards/src/non_fungible_token/core/core_impl.rs)

Track the entries by token and transfer ID with a per-token count and O(1) insertion/resolution, without scanning the chain of owners. Fund temporary entries from issuer storage and size that reserve using concurrent callback tests. Avoid a one-entry lock that disables standard onward transfer. A finite storage pool can reject new transfer-calls on exhaustion, while plain transfers retain their standard path. A wedged resolver consumes storage until reviewed repair. Exact funding limits and recovery interfaces are Phase 1 design checks.

Run real receiver contracts through NEAR Workspaces in Phase 1, and repeat representative cases on testnet after authorization. Cover false/accept, true/return, receiver panic, absent method, malformed return, private resolver access, duplicate resolver, and resolver failure. Test onward plain transfer before rollback, nested transfer-calls resolving in either order, and the receiver regaining ownership before resolution. Compare owner, enumeration, return disposition and events against the pinned standard. Assert epoch changes, the pending compute hold through every receipt, settlement/refund during the hold, and rejection of pre-transfer permits after restoration. No compatibility result is claimed until these tests run. [Workspaces](https://github.com/near/near-workspaces-rs)

## Storage, dispatch and spend

The Phase 1 interfaces and fixed storage budgets are recorded in [Contract API](CONTRACT_SPEC.md) and [Accounting invariants](ACCOUNTING_INVARIANTS.md).

Prepay issuer storage for bounded live passes, reservation slots and temporary pending transfer entries. Measure actual storage and callback gas using maximum supported IDs, and reject writes lacking prepaid capacity. Delete terminal liability rows while keeping a monotone replay counter. Preserve immutable issuer/policy boundaries and the conservation equation from the plan.

Use transactional idempotency and outbox, a durable dispatch fence before upstream I/O, no generation retries, and conservative settlement after ambiguous outcomes. PostgreSQL, NEAR and the provider have independent failure boundaries. A trusted gateway can enforce one application send attempt. Provider processing and billing remain independently observed. Public sponsored inference requires provider permission, an isolated project, bounded request caps, funded issuance, provider-side spend controls where available, and issuer/day/global admission limits.

## Evidence gates

Conservation, ownership checks, replay resistance, privacy and bounded settlement are correctness requirements to test before release. Performance percentiles, provider limits, wallet support and public-service budgets are validation targets. Toolchain pins cover only the verified foundation. Wallet and provider versions remain candidates until concrete wallet signing, account-specific calls and deployment prerequisites pass. No billing or live support claim follows from docs alone.
